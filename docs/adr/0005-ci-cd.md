# ADR 0005: GitHub Actions gates Render deployments

- Status: Accepted
- Date: 2026-11-01

## Decision

Use a protected promotion chain: feature branches merge into `dev`, tested release candidates promote from `dev` to `staging`, and reviewed production releases promote from `staging` to `main`. Do not merge `dev` directly to `main`. Require the same CI status on all three branches and disallow force-pushes/deletions in the hosting platform.

GitHub Actions runs Ruff, Python compilation, unit tests, Compose validation, and the production Docker build on pull requests and pushes to `dev`, `staging`, and `main`. Connect separate Render services to the matching branches; production remains connected only to `main`. Render deploys after successful checks. Secrets live in environment configuration, not the repository or CI workflow.

`compose.dev.yaml` and `compose.staging.yaml` mirror the Render process shape: one non-root Docker web service, PostgreSQL 16 with pgvector, startup migrations, health checks, the pinned CPU provider, and environment-only configuration. Matching can start enabled but remains fail-closed with `503` until the reference gallery is loaded. They are local parity environments, not substitutes for Render branch protection or managed secrets/TLS.

## Consequences

Promotion requires branch protection and three independently configured Render services. Render Free still lacks pre-deploy commands, so each service runs backward-compatible migrations at startup. Destructive migrations require an expand/migrate/contract rollout and must not be coupled to one branch promotion.
